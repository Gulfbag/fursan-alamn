# النواة الرقمية — العمل بلا ورق

## الهدف والنطاق

واجهة إدارة داخلية واحدة، لا سلسلة من نماذج Sheets ومشغلات Gmail. تبدأ قاعدة مستقلة فارغة، وتبقى Master وDrive والسكربتات القديمة خارج صلاحياتها. النواة **إصدار اختبار** وليست نظام ERP أو تطبيق الحارس أو غرفة مراقبة الفيديو أو إطلاقًا إنتاجيًا.

المساران `/operations.html` و`/en/operations.html` يستعملان API حقيقية فقط. لا role switch أو بيانات عرض أو حفظ أعمال في localStorage. استضافة GitHub Pages تعرض الحالة غير المتصلة ولا تستطيع حفظ سجل. لا تعرض الواجهة نجاحًا قبل رد API.

## دورة يومية بلا ورق

1. سجّل طلبًا وعنوانًا ونطاقًا؛ معلومات الاتصال اختيارية فلا تختلق بيانات أشخاص لمهمة داخلية.
2. اربطه بعميل عند الحاجة، ثم أنشئ مهمة مسؤولة ومؤرخة.
3. انتقل من جديد إلى المراجعة ثم التنفيذ، وحدّث الحالة بعد إثبات العمل.
4. أنشئ ملف عمل: إجراء، تقرير خدمة، مقترح، مراسلة. محتواه نص رقمي محفوظ بالإصدارات.
5. أرسله للمراجعة ثم يعتمد مدير أو admin **مستقل** نسخته داخليًا؛ لا يجوز للمنشئ أو آخر من عدّل المحتوى الاعتماد، حتى لو كان admin. أي تعديل فعّال لعنوان الملف أو نوعه أو محتواه أو روابطه أثناء المراجعة يعيده ذريًا إلى `draft` ويستلزم `in_review` جديدة. لا يمكن تعديل النص المعتمد صامتًا؛ مراجعة جديدة تعيده لمسودة.
6. استرجع سجل النسخ والتاريخ وبصمة المحتوى، أو صدّر Markdown وتقرير JSON. لا يرسل النظام بريدًا أو واتساب أو عقدًا تلقائيًا.

ليس الاعتماد الداخلي توقيعًا قانونيًا أو موافقة على سجل حكومي أو مالي. تحميل المرفقات/OCR والتوقيع الإلكتروني القانوني وتصدير PDF المنسق وإشعارات البريد والمهام الدورية مراحل لاحقة، لا وظائف مفعلة في هذه النواة. لا تستبدل أي إجراء نظامي يتطلب مستندًا أو توقيعًا معتمدًا بمجرد هذا السجل.

## الهوية والحفظ

- JWT IAP موقع ES256، issuer وaudience وكيد صحيحون؛ البريد والدور لا يأتيان من browser/body/ترويسة غير موقعة.
- `OPS_ROLE_BINDINGS` خادمي: admin/manager يديران، operator يكتب ما أنشأه أو ما أسند إليه، viewer قراءة. قراءة operator منظمة-wide في هذا الإصدار للتنسيق؛ تحتاج مراجعة قبل إتاحة بيانات حساسة لفريق أوسع.
- يسجل الخادم في كل ملف جديد `createdBy` و`lastContentEditedBy` من subject الموثق؛ لا يقبل العميل الحقل الثاني في body. تسجل مراجعة المستند هوية منشئ المراجعة وآخر محرر محتوى معروفًا أو `null` إن لم يمكن إثباته، ويسجل audit هوية منفذ العملية. قرار الاعتماد يفحص subject الحالي داخل معاملة الإصدار نفسها مقابل المنشئ وآخر محرر محتوى.
- **تغيير المخطط والتوافق:** لا توجد هجرة أو backfill تلقائيان عند القراءة. المستندات القديمة التي لا تملك `lastContentEditedBy` تبقى قابلة للقراءة، لكن لا تعتمد: إذا كان الطالب هو المنشئ يرد `self_approval_forbidden` (403)، وإلا يرد `approval_identity_unverified` (409) بدل تخمين محرر محتوى من `createdBy`. يستعيد الملف قابلية الاعتماد فقط بعد تعديل محتوى فعّال يملأ الحقل خادميًا ويعيده إلى `draft` ثم `in_review`. لا يحاول الخادم استنتاج المحرر عبر قراءة سجل نسخ غير محدود؛ يظل سجل المراجعات المعروض محدودًا بآخر 200 revision IDs.
- Firestore خادمي ADC في قاعدة **مسماة**، مع IAM condition دقيقة للقاعدة وحدها؛ لا صلاحية على Master ولا مفتاح خدمة جديد.
- الإنشاء والتعديل والحالة وسجل التدقيق وreceipt التكرار ونسخة المستند معاملة واحدة. UUID idempotency + version conflict يمنعان تكرار الحفظ وتعديل نسخة قديمة.
- الخادم يحدد ID/org/actor/status/timestamps؛ رفض الحقول الغريبة وRole forgery وOrigin والـintent غير المطابقين. لا DELETE للسجلات أو تعديل audit في API.
- البحث prefix لكلمة واحدة، أو تصفية حالة، وليس كلاهما؛ تحميل القوائم pagination ≤100. التقارير محدودة حتى1000 لكل نوع وموضحة truncated.
- حدود المعدل داخلinstance واحد فقط؛ إعداد Staging max1 ليس سقف فاتورة ولا حماية موزعة إنتاجية.

## الذكاء الذي شُغّل والذي لم يشغّل

المساعد المحلي **قواعد إجرائية ثابتة** لترتيب المعطيات وإعداد خطوات أو مراسلة أولية، وليس LLM. ناتجه غير محفوظ حتى يختار المستخدم حفظ ملف رقمي؛ لا ينفذ أو يعتمد أو يرسل.

موصل Vertex مهيأ في الشيفرة فقط ومعطل افتراضيًا. يتطلب قرارًا مستقلًا عن النموذج والمنطقة والبيانات وإذن IAM. لا endpoint عالميًا كبديل ولا نقل خارج منطقة معتمدة صامتًا. لا تمرر بريدًا أو هاتفًا أو اسم اتصال في payload المقيد، والوصف قد يتضمن PII فيتطلب تصنيفًا وموافقة بشرية non_sensitive للإصدار الحالي. موافقة AI ليست آلية إزالة PII أو شهادة امتثال. المخرجات مسودات ذات مصدر واحد وحدود حجم ومراجعة؛ لا توظيف أو قرارات أمنية تلقائية.

## قبول Staging قبل إعلان الحفظ الدائم

اختبارات المصدر المعزولة لا تثبت SDK/ADC. يلزم التحقق من القاعدة والإذن الحقيقيين ثم إنشاء بيانات مصطنعة محدودة واسترجاعها بعد تحديث الصفحة، تكرار نفس key، version conflict، دورة المستند والتدقيق، رفض المجهول/role/origin وفشل الحفظ، وعرض الجوال. لا تمنح دورًا أوسع لتجاوز خطأ IAM أو فوترة.

الإعداد في `.env.example`؛ `OPS_ENABLED=false` افتراضيًا، وطلب التفعيل بإعداد ناقص يرفض startup. Master/AI/LEAD_SINK تظل معطلة كل منها مستقلًا. قبل الإنتاج: الاحتفاظ والمراقبة واستعادة مجربة وحسابات الموظفين وعزل الوصول والتوقيع والمتطلبات النظامية. PITR وحماية الحذف لا تعني نجاح اختبار استعادة.
